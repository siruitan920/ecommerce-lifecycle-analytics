# 埋点需求与数据采集改进

这份数据是第三方平台（REES46 Open CDP）采集的现成日志，没法改。这里写的是：**做完这个项目之后，
如果我是这家平台的数据分析师，会向产品和研发提哪些埋点需求**——每一条都对应分析里实际卡住的地方。

## 1. 现有事件

| 事件 | 触发时机 | 关键字段 | 问题 |
|---|---|---|---|
| view | 浏览商品详情 | user_id, user_session, product_id, category_code, brand, price | 32% 的商品没有品类编码；没有来源渠道 |
| cart | 加入购物车 | 同上 | 没有数量；没有对应的 remove_from_cart（数据集说明里有，但这两个月没采到） |
| purchase | 购买 | 同上 | 没有 order_id、订单金额、币种；**11-14 ~ 11-17 中断 48 小时** |

## 2. 采集中断复盘

- **现象**：本地 11-14 22:00 ~ 11-16 10:59、11-16 19:00 ~ 11-17 05:59，purchase 事件全部丢失，浏览和加购正常（定位过程见 notebook 01）；
- **影响**：大促三天中两天的 GMV、转化率不可用；一批看似合理的结论（大促前段只加购不下单、周五转化最低）都是数据缺失造成的；
- **为什么没被发现**：没有按事件类型的量级监控。日 GMV 归零这种程度的异常，靠人看日报要到第二天才会发现，48 小时的缺口在复盘时才被注意到；
- **改进**：见第 4 节监控规则。按「purchase 小时量低于上周同时段 0.3 倍」告警，这次中断开始后 1 小时内就能报出来。

## 3. 新增与修改的埋点需求

优先级：P0 = 不补就无法回答核心问题；P1 = 明显提升分析质量；P2 = 锦上添花。

| 优先级 | 事件 / 字段 | 触发时机 | 关键属性 | 解决什么问题 |
|---|---|---|---|---|
| P0 | purchase 增加 `order_id`、`order_amount`、`currency`、`quantity` | 支付成功 | | 现在只能用 session 近似订单，金额不知道币种，GMV 无法换算 |
| P0 | `app_open` / `page_view`（会话入口） | 打开 App / 进入站点 | `source`, `medium`, `campaign`, `landing_page` | 没有渠道来源，**做不了渠道转化漏斗**；DAU 涨了不知道是哪个渠道带来的（notebook 02 的 11-04） |
| P0 | `push_sent` / `push_open` / `sms_sent` | 消息发出 / 被点开 | `message_id`, `template`, `trigger_reason` | 召回实验的处理变量；没有它无法区分「自然回流」和「被召回」 |
| P0 | `experiment_exposure` | 用户进入实验分组时 | `experiment_id`, `variant`, `assign_time` | A/B 实验分组记录，用于 SRM 检查和效果归因 |
| P0 | `notification_disable` / `unsubscribe` | 关闭推送 / 退订 | `channel` | 召回实验的护栏指标 |
| P1 | `remove_from_cart` | 移出购物车 | `product_id`, `quantity` | 区分「放弃」和「还在购物车里」 |
| P1 | `coupon_issue` / `coupon_redeem` | 发券 / 用券 | `coupon_id`, `face_value` | 召回成本核算；区分「券带来的购买」 |
| P1 | `refund` / `return` | 退款 / 退货 | `order_id`, `amount` | 现在的 GMV 是毛 GMV，没法算净 GMV |
| P1 | 用户属性：`country`, `language`, `device`, `platform` | 会话开始 | | 跨境业务按国家/站点拆分；时区现在只能从流量曲线推断 |
| P1 | 活动日历（维表，不是事件） | 运营配置 | `campaign_id`, `start`, `end`, `type` | 大促窗口现在只能从流量识别 |
| P2 | `search` | 搜索 | `query`, `result_count` | 需求侧分析、无结果搜索 |
| P2 | 商品维表补全品类映射 | | | 32% 的事件品类为空，品类分析有一块盲区 |

## 4. 数据质量监控规则

| 规则 | 粒度 | 阈值 | 动作 |
|---|---|---|---|
| 各事件类型量级 vs 上周同时段 | 小时 | < 0.3 倍（且该小时流量正常） | 立即告警，通知埋点负责人 |
| 全量事件 vs 上周同时段 | 小时 | < 0.6 倍 | 告警 |
| purchase / cart 比值 | 日 | 偏离近 14 天均值 3 个标准差 | 告警（埋点异常或真实业务变化，人工判断） |
| 关键字段空值率 | 日 | user_id、event_time、price 任何空值；category_code 空值率比上周高 5 个百分点 | 告警 |
| 枚举值 | 日 | event_type 出现新值 | 告警 |
| 跨层对账 | 每次跑批 | 购买件数、GMV 在各层不一致 | 跑批失败 |

本项目里已实现的部分在 `pipeline/quality_checks.py`，结果见 `docs/data_quality_report.md` 和看板「数据质量」页。

## 5. 口径对齐清单

上线新指标或对外汇报前，和产品、运营对齐这几件事：

- [ ] 「活跃」包括哪些事件？只打开不浏览算不算？
- [ ] 一笔订单怎么定义？拆单、合并支付怎么算？
- [ ] GMV 含不含取消、退款？用下单时间还是支付时间？
- [ ] 日期按哪个时区切？跨境多站点是否统一？
- [ ] 「新用户」是首次访问、首次注册还是首次下单？
- [ ] 留存是「第 N 天当天」还是「N 天内」？
- [ ] 流失的沉默天数阈值是多少？依据是什么？
